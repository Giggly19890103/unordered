[[header]]
== 常规容器

[[content]]
[[preamble]]
Boost.Unordered
的闭寻址容器（`boost::unordered_set`、`boost::unordered_map`、`boost::unordered_multiset`
与 `boost::unordered_multimap`）完全符合 C++
无序关联容器的标准规范。因此，对于熟悉`std::unordered_set`、`std::unordered_map`
等用法的用户，可直接将其替换为Boost.Unordered
中的同名容器。开放寻址容器（`boost::unordered_node_set`、`boost::unordered_node_map`、`boost::unordered_flat_set`
和
`boost::unordered_flat_map`）的接口与之高度相似，但存在一些细微差异，详见专门的
link:compliance.html#compliance_open_addressing_containers[标准符合性章节]。

对于没有哈希容器经验但熟悉常规关联容器（`std::set`、`std::map`、`std::multiset`
和 `std::multimap`）的读者，Boost.Unordered 容器的使用方式与之类似：

[source,highlight]
----
typedef boost::unordered_map<std::string, int> map;
map x;
x["one"] = 1;
x["two"] = 2;
x["three"] = 3;

assert(x.at("one") == 1);
assert(x.find("missing") == x.end());
----

但由于元素不按顺序存储，以下代码的输出结果：

[source,highlight]
----
for(const map::value_type& i: x) {
    std::cout<<i.first<<","<<i.second<<"\n";
}
----

可能以任意顺序输出。例如，结果可能为：

[source,highlight]
----
two,2
one,1
three,3
----

其他差异列于 link:regular.html#comparison[与关联容器的对比] 章节中。

[[regular_iterator_invalidation]]
== 迭代器失效

标准未明确规定除`rehash` 和 `reserve`
之外的成员函数如何影响桶数量，但`insert`
操作仅当导致容器负载超过最大允许值时才会使迭代器失效。在大多数实现中，这意味着
`insert`
仅在此种情况下才会改变桶的数量。迭代器可能因调用`insert`、`rehash` 或
`reserve` 而失效。

对于基于节点的容器（`boost::unordered_[multi]set`、`boost::unordered_[multi]map`、`boost::unordered_node_set`、`boost::unordered_node_map`），其指针和引用永远不会失效。但对于
`boost::unordered_flat_set` 和
`boost::unordered_flat_map`，在发生重哈希时指针和引用将会失效：这是因为这些容器将元素直接存储在桶中，当分配新的桶数组时，必须通过移动构造来转移元素。

类似于对 `vector` 使用 `reserve` 的方法，在插入大量元素前先调用
`reserve`
是推荐做法。这将避免昂贵的重新哈希操作，并确保迭代器在后续插入中保持有效。若需向容器
`x` 插入 `n` 个元素，可先调用：

[source,highlight]
----
x.reserve(n);
----

注意::
  `reserve(n)` 为至少 `n`
  个元素预留空间，通过分配足够的桶数量来确保容器负载不超过最大负载因子。
  +
  由于最大负载因子被定义为元素数量与可用桶总数之比，该函数在逻辑上等效于：
  +
[source,highlight]
----
x.rehash(std::ceil(n / x.max_load_factor()))
----
  +
  关于 `rehash`
  函数的link:reference/unordered_map.html#unordered_map_rehash[详细信息请参阅参考文档]。
